## Focus

WCAG 2.1 AA compliance for all frontend views: semantic HTML, ARIA, forms, keyboard navigation, contrast, touch targets.

**Complete guidelines:** Read guidelines/accessibility.md AND guidelines/accessibility-2026.md in the skill directory and check the code against all rules described there.

**For native apps** (`FRAMEWORK` = ios/android/react-native/flutter): use `guidelines/native-mobile.md` section I instead — accessibilityLabel/contentDescription, Dynamic Type, touch targets 44pt/48dp, VoiceOver/TalkBack groups, reduced motion. WCAG/ARIA HTML rules do not apply there.

## Verify-Before-Flag (MANDATORY, dominant FP source)

These four patterns were the most frequent false-positive source in two consecutive audit runs. Before flagging, ALWAYS check against the actual DOM/AT tree, not just the single line:

1. **Missing `aria-label`** — first check whether the element already has visible text, a `<title>`, `aria-labelledby`, or an associated `<label>`. An icon-only button with adjacent text label is not a finding.
2. **Label association** — `for`/`id` or a wrapping `<label>` can be several lines away. Read the whole block before reporting "label not associated."
3. **`x-show`/`display:none` visibility** — an element hidden via `x-show`/`x-cloak`/`hidden` is not necessarily a contrast/focus issue; check whether it is even reachable in its visible state.
4. **Tailwind classes in PHP/Blade strings** — classes can be set via `@class([...])`, ternary PHP expressions, or concatenated strings. Before reporting "class missing," trace the compiled/assembled value, not just the HTML attribute.

Still uncertain after checking → do NOT flag (or flag as `confidence: low` with an explicit note of what remained unchecked).

## Widget Checklist (MANDATORY for findings on custom widgets)

As soon as you report ANY finding on an interactive custom widget (`role="radiogroup"`, `role="tablist"`, `role="listbox"`, `role="menu"`, `role="slider"` or similar), ALWAYS check the entire widget, not just the flagged property:

1. **Keyboard operability**: arrow keys (left/right or up/down), Home/End, Space/Enter to activate. A roving tabindex WITHOUT arrow-key handlers makes the widget unusable for keyboard users — its own finding, at least Important.
2. **Roving tabindex**: exactly one element with `tabindex="0"`, the rest `-1`, focus moves with selection.
3. **aria states**: `aria-checked`/`aria-selected`/`aria-expanded` present AND dynamic (Alpine binding, not static).

Lesson learned: a contrast Critical was found on a radiogroup, the missing arrow-key handlers on that same radiogroup only surfaced in the follow-up audit.

**Custom accessibility actions per element:** count `.accessibilityAction`/custom accessibility actions attached to a single row/element (VoiceOver rotor entries), including any inherited from a shared row/cell component. >= 8 on one element is an Important finding (VoiceOver rotor overload) — cite the element and the exact count. Real case 2026-07-02: ShoppingListView row hit 9 custom actions, noted only as a follow-up, not flagged.
